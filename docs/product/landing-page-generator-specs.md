## 1. Product Vision

Sarani produces campaign assets for clients like Sony, TikTok, GEODIS, and L'Oréal. Today, when a client needs a landing page — for a product launch, a seasonal campaign, or an event — Sarani must either brief an external developer or manually assemble a page, adding 2 to 5 days to the delivery cycle. This contradicts the core promise: "Ultra-fast, Deliver-Always, D+1 delivery."

The **Landing Page Generator** turns the back-office into a fully autonomous landing page production tool. Given a brief, a client record, and optional visuals, the system generates a complete, branded, publicly accessible landing page in minutes — ready for client validation, iterable on demand.

**Problem solved:** Sophie (Head of Marketing) needs a campaign landing page for a product launch on Wednesday. Today she waits 3–5 business days and pays a markup on development. With this feature, her Sarani account manager generates a production-ready page in under 30 minutes, shares a link for client approval, and iterates live on the copy, visuals, and palette within the same session.

**For whom:** the Sarani team (Thomas + client managers) — not the client directly. The client receives a shareable preview link (same pattern as `/preview/[token]` for video previews) and provides feedback via Approve / Request Changes.

**V1 scope:** AI-generated copy (hero, features, social proof, CTA, footer), client brand identity applied (colors, font, logo), layout from a fixed set of section templates, hosted as a server-rendered Next.js dynamic route under `/lp/[slug]`, shareable by secure link. No drag-and-drop visual editor in V1 — iteration is form-based (edit brief fields → regenerate).

**Link to North Star:** landing page delivery is a new billable service tier (estimated €500–2,500 per page based on benchmark). Faster turnaround = more projects per client per quarter = path toward 10M€ CA at 20% EBITDA. Each landing page generated also showcases Sarani's creative + tech capability to Sophie's team, reinforcing retention.

## 3. User Stories

### US-LP-01 — Create a landing page from a brief and a client record

**Given** a client exists in the Sarani DB with at least `name`, `primaryColor`, and `fontName` filled,
**When** a client manager fills the "New Landing Page" form (brief + client selection + optional visuals upload) and clicks "Generate",
**Then** the system calls the LLM with the brief, client identity, and brand guidelines, generates all copy sections (hero headline, subheadline, feature bullets, social proof block, CTA text, footer tagline), applies client colors and font, and creates a `landingPages` record with status `generating` — then transitions to `ready` when all sections are populated.

**Acceptance criteria:**
- The "Generate" button is disabled until `brief` (min 50 chars) and `clientId` are filled
- Estimated generation cost is displayed before confirmation: "Generating this page will use approximately X tokens — estimated cost: $0.05. Confirm?"
- Generation is async: the user sees a progress indicator (skeleton page sections appearing one by one as the LLM streams)
- If client `brandTone` is filled, the LLM prompt instructs the model to match that tone
- If client `brandGuidelinesNotes` is filled, those notes are injected into the system prompt as constraints
- On success: redirect to the Landing Page detail view with the generated content pre-populated
- On LLM failure: status set to `error`, message "Generation failed — please retry or adjust the brief", retry button visible

**Edge cases:**
- Client has no `primaryColor` filled: warning shown before generation ("This client has no primary color configured — the page will use Sarani default colors. Continue or update the client record first?")
- Brief under 50 chars: inline validation "Brief too short — add more context about the campaign goal, target audience, and key message"
- Brief over 3,000 chars: warning "Long briefs may produce unfocused copy. Consider trimming to the essential campaign goal."
- LLM timeout (>30s): status `error`, "AI generation timed out — please retry"

### US-LP-02 — Preview the generated landing page

**Given** a landing page has been generated (status `ready`),
**When** a client manager opens the Landing Page detail view in the back-office,
**Then** a live preview of the rendered page is shown in an iframe (responsive toggle: desktop / mobile), with all generated copy and the client's brand identity applied.

**Acceptance criteria:**
- The preview iframe renders `/lp/[slug]?preview=true` — same component as the public page, no separate renderer
- Responsive toggle: two buttons "Desktop" and "Mobile" — switches the iframe width (1200px / 390px)
- All five UI states are visible per section: default (rendered content), loading (skeleton), empty (if a section has no content), error (if a section failed to generate), success (green border on freshly generated sections)
- The preview updates within 2 seconds of saving any field edit
- "View public page" button opens `/lp/[slug]` in a new tab

**Edge cases:**
- Generated copy contains Markdown formatting: rendered as HTML (bold, line breaks preserved), not displayed as raw syntax
- Font specified in client record is not a Google Font: fallback to Outfit (Sarani default), warning displayed "Font '[fontName]' could not be loaded — using Outfit as fallback"

### US-LP-03 — Iterate on a landing page (content, visuals, colors)

**Given** a landing page has been generated (status `ready` or `published`),
**When** a client manager edits any field in the iteration panel (brief, copy overrides, color palette, logo, visual assets) and clicks "Regenerate" or "Apply",
**Then** the system either re-runs the LLM for the modified sections (if brief or copy changed) or applies CSS/asset changes without LLM (if only palette or visuals changed), and creates a new version record in `landingPageVersions`.

**Acceptance criteria:**
- "Apply" (no LLM call) is available for: palette swap, logo swap, individual visual replacement
- "Regenerate" (LLM call) is required for: brief edit, individual section copy edit with "AI re-write" mode, full page regen
- Each saved iteration creates a new version row (version number increments)
- Previous versions are accessible via a "Version history" dropdown (max 10 versions kept)
- The user can restore any previous version ("Restore v3")
- Cost is shown before any LLM call: "Regenerating hero section — estimated $0.01. Confirm?"
- A section can be manually overridden: user types copy directly into the field, marks it as "manual override" — subsequent full-page regenerations do NOT overwrite manually overridden sections (unless user explicitly clears the override)

**Edge cases:**
- Regeneration while page is `published`: page stays live on the previous version until the user explicitly clicks "Publish new version"
- All sections manually overridden: "Regenerate all" button greyed out with tooltip "All sections are manually overridden — clear overrides to enable AI regeneration"
- Version history full (10 versions): oldest version auto-deleted after user confirmation "Version 1 will be deleted to save space — confirm?"

### US-LP-04 — Publish the landing page on a public URL

**Given** a landing page is in status `ready`,
**When** a client manager clicks "Publish",
**Then** the page becomes publicly accessible at `/lp/[slug]` without authentication, the status changes to `published`, and the public URL is displayed with a copy-to-clipboard button.

**Acceptance criteria:**
- Slug is auto-generated from client name + brief title (e.g., `sony-black-friday-2026`), editable before publishing
- Slug uniqueness enforced: if slug already exists, auto-append `-2` suffix (or prompt user to rename)
- Published page is indexed by default: `<meta name="robots" content="index, follow">` unless user toggles "Private (no-index)"
- `sitemap.xml` is not auto-updated in V1 [HYPOTHÈSE H-02 : dynamic sitemap to include `/lp/` routes — implementation complexity to assess]
- Unpublish available at any time: page returns 404, status back to `ready`
- "Published since [date]" badge visible in the back-office detail view

**Edge cases:**
- Publishing a page with an empty section: warning "Section 'Social Proof' is empty — the page will be published without it. Continue?"
- Slug conflict with existing site routes (e.g., `/lp/about`): blocked by a reserved slug list, error "This URL is reserved — choose a different slug"

### US-LP-05 — Share the landing page with the client for validation

**Given** a landing page is in status `ready` or `published`,
**When** a client manager clicks "Share with client",
**Then** a secure share token is generated (UUID, valid 14 days), and the client receives access to `/preview/lp/[token]` — a read-only version of the page with an "Approve" button and a "Request changes" button, without requiring Sarani login.

**Acceptance criteria:**
- The share link is accessible without a Sarani account
- The preview page displays: Sarani "Preview — not for distribution" watermark banner at the top
- "Approve" button: records approval with timestamp, IP, and client name (from `landingPages.clientId`) — no account required
- "Request changes" button: opens a textarea (max 1,000 chars), submits feedback stored in `landingPageFeedback` table, triggers email notification to the client manager
- Token expires after 14 days (configurable per page)
- Token can be manually revoked from the back-office
- Link copy-to-clipboard button in back-office
- Status tracking in back-office: Not shared / Shared / Viewed / Approved / Changes requested

**Edge cases:**
- Expired token: page displays "This preview link has expired — please contact your Sarani account manager"
- Revoked token: same message
- Client approves after the page was unpublished: 404 with message "This page is no longer available"
- Client submits empty "Request changes" text: inline validation "Please describe the changes you'd like"

### US-LP-06 — Duplicate a landing page (for A/B variants or new campaigns)

**Given** a landing page exists in any status,
**When** a client manager clicks "Duplicate",
**Then** a new `landingPages` record is created with all fields copied (brief, sections, client, palette), status set to `draft`, slug suffixed with `-copy`, and the user is redirected to the new page's edit view.

**Acceptance criteria:**
- All section content is copied verbatim (no re-generation)
- Visual assets are referenced (not duplicated in storage) — shared by reference
- The duplicate has no share token and no approval record (fresh slate)
- Version history is NOT copied (new page starts at version 1)
- The duplicate is clearly labeled in the list view with "Copy of [original name]"

**Edge cases:**
- Original page is deleted after duplication: visuals referenced but missing → fallback to client logo only, warning displayed in edit view
- Duplicating a page with manual overrides: overrides are preserved in the copy

### US-LP-07 — List and manage all landing pages for a client

**Given** a client manager is in the Landing Pages section of the back-office,
**When** they view the list,
**Then** they see all landing pages (all clients or filtered by client), with status badges, creation date, public URL, last edit date, and share status — sortable by creation date and status.

**Acceptance criteria:**
- List columns: Page title / Client / Status / Public URL / Last modified / Share status / Actions
- Status badges: Draft / Generating / Ready / Published / Archived
- Filter by client (dropdown from clients DB)
- Filter by status
- "Archive" action: sets status to `archived`, removes from published routes (returns 404)
- "Delete" action: hard delete with confirmation modal — only available on `draft` and `archived` pages

**Edge cases:**
- No landing pages yet: empty state with "Create your first landing page" CTA
- More than 50 pages: pagination (20 per page)

### US-LP-08 — Display estimated AI cost before any generation

**Given** any LLM call is about to be triggered (full generation, section regen, or copy rewrite),
**When** the user clicks any generation button,
**Then** a confirmation modal displays: estimated token count, estimated USD cost, and a "Confirm" / "Cancel" button — generation does not start without confirmation.

**Acceptance criteria:**
- Token estimate based on: brief length + client guidelines length + section template prompts (precalculated by model)
- Cost formula displayed: "[X] input tokens + [Y] output tokens × [model rate] = ~$[Z]"
- Model used is displayed: "Claude Haiku" or "Claude Sonnet" depending on task (Haiku for copy regen, Sonnet for full page)
- Actual token cost is stored post-generation in `landingPages.totalTokenCost` (integer, cumulative per page)
- A "generation history" tab in the page detail shows all LLM calls with actual costs

**Edge cases:**
- Estimate unavailable (API error): show "Cost estimation unavailable — generation will still proceed. Confirm?"
- Zero-cost operation (palette swap, logo swap): no modal — changes apply immediately

## 4. Architecture technique

### 4.1 Content Generation — LLM pipeline

**Model selection:**
- Full page generation (all sections): Claude Sonnet (`claude-sonnet-4-6`) — quality over cost, full brand context needed
- Single section regeneration: Claude Haiku — faster, cheaper, sufficient for targeted rewrites
- Brief analysis / "AI brief check" (pre-generation): Claude Haiku — lightweight validation

**Generation pipeline:**

```
[Form submission]
       ↓
[Build system prompt]
  - Role: "You are a senior copywriter at Sarani, a creative agency producing landing pages
           for enterprise clients. You write high-converting, brand-aligned copy."
  - Client context: name, industry, brandTone, brandGuidelinesNotes, primaryLanguage
  - Brand constraints: primaryColor (hex), fontName, prohibitedTerms (if any)
  - Brief: full text from the form
  - Output format: structured JSON with section keys
       ↓
[POST to Anthropic API — streaming]
       ↓
[Parse JSON response → populate landingPageSections]
       ↓
[Save to DB: landingPages + landingPageVersions]
       ↓
[Redirect to detail view]
```

**Output JSON schema (LLM target format):**
```json
{
  "hero": {
    "headline": "string (max 80 chars)",
    "subheadline": "string (max 160 chars)",
    "ctaText": "string (max 30 chars)",
    "ctaUrl": "string (placeholder '#contact' if not specified in brief)"
  },
  "features": [
    { "icon": "string (lucide icon name suggestion)", "title": "string (max 40 chars)", "description": "string (max 120 chars)" }
  ],
  "socialProof": {
    "quote": "string (max 200 chars)",
    "author": "string",
    "company": "string"
  },
  "cta": {
    "headline": "string (max 80 chars)",
    "subtext": "string (max 120 chars)",
    "buttonText": "string (max 30 chars)"
  },
  "footer": {
    "tagline": "string (max 100 chars)"
  },
  "meta": {
    "title": "string (max 60 chars, SEO-optimized)",
    "description": "string (max 160 chars, SEO-optimized)"
  }
}
```

**Error handling:**
- If LLM returns invalid JSON: retry once with a stricter prompt ("Return ONLY valid JSON, no markdown code blocks")
- If second attempt fails: status → `error`, store raw LLM output for debugging in `landingPages.rawLlmOutput`
- Streaming timeout (>45s): abort, status → `error`

### 4.2 Rendering — Next.js dynamic route

**Route:** `src/app/lp/[slug]/page.tsx` — Server-Side Rendered (SSR), no static generation in V1.

**Why SSR over static:**
- Pages are iterated frequently (multiple versions per day possible)
- Static generation (ISR) would require revalidation on every save — adds complexity with no performance gain for low-traffic preview pages
- SSR renders fresh on every request, which is correct for preview links and iteration loops

**Route logic:**
```
GET /lp/[slug]
  → DB lookup: landingPages WHERE slug = [slug] AND status = 'published'
  → If not found: 404
  → Render LandingPageTemplate with: sections, client colors, font, logo URL

GET /preview/lp/[token]
  → DB lookup: landingPageShareTokens WHERE token = [token] AND expiresAt > NOW()
  → If not found or expired: render "Link expired" page
  → Render LandingPageTemplate with: sections + preview watermark banner + Approve/Request Changes UI
```

**CSS application:** client brand identity applied via CSS custom properties injected server-side into the page `<head>`:
```html
<style>
  :root {
    --brand-primary: #DA5126;   /* from client.primaryColor */
    --brand-secondary: #0BABE8; /* from client.secondaryColors[0] or Sarani default */
    --brand-font: 'Outfit', sans-serif; /* from client.fontName, loaded via Google Fonts */
  }
</style>
```

All landing page components reference these CSS variables — swapping a client's palette is a single DB field update.

### 4.3 Visual assets storage

**Logo:** stored as a URL in the `clients` table (future: `logoUrl` field to add). V1: upload to SharePoint via Microsoft Graph API (already integrated), store SharePoint URL in the `landingPages.logoUrl` field.

**Product visuals / images:** uploaded per landing page, stored in SharePoint under `/Sarani Back-Office/Landing Pages/[clientId]/[landingPageId]/`. URLs stored as JSON array in `landingPages.visualAssets`.

**[HYPOTHÈSE H-03 : SharePoint public URL access for images]** SharePoint links may require authentication to render in a public page. If so: proxy images via a Next.js API route (`/api/lp/asset/[assetId]`) that fetches from SharePoint server-side and streams the response. This adds latency (~200ms per image) but keeps all assets in SharePoint for consistency. Alternative: Replit Object Storage for public assets. Thomas to decide.

**File size limits:** 5MB per image, 10MB for logo SVG/PNG. Enforced client-side before upload.

### 4.4 Section templates (layout)

V1 offers **one layout** with configurable sections. The account manager selects which sections to include:

| Section | Required | Configurable |
|---|---|---|
| Navbar (logo + CTA button) | Yes | CTA text + URL |
| Hero (headline + subheadline + CTA + background image or color) | Yes | Background: client color or uploaded image |
| Features (3-column grid, icon + title + description) | Optional | 2 to 6 features |
| Social proof (quote + author + company) | Optional | Single quote V1; carousel V2 |
| CTA section (headline + subtext + button) | Yes | Color: brand primary |
| Footer (logo + tagline + client name) | Yes | Tagline from LLM or manual override |

V2: additional layout templates (left-right split hero, full-bleed video background, minimal one-pager).

---

### 4.5 Public page performance & SEO

- **Meta tags:** `<title>` and `<meta name="description">` generated by LLM (output in `meta` JSON block)
- **OG tags:** `og:title`, `og:description`, `og:image` (first uploaded visual or client logo), `og:url`
- **Canonical:** `<link rel="canonical" href="https://sarani.studio/lp/[slug]">`
- **Fonts:** loaded via Google Fonts `<link>` in `<head>` — Next.js font optimization (next/font) if font is Outfit; raw Google Fonts URL otherwise
- **Images:** `next/image` with `width`/`height` for CLS prevention
- **No-index option:** `<meta name="robots" content="noindex, nofollow">` when user toggles "Private"
- **Lighthouse target:** Performance >= 85, Accessibility >= 90 (WCAG AA contrast respected via design token usage)

## 5. Data Model

New tables to add to `src/lib/db/schema.ts`. All follow the existing pattern (UUID PKs, timestamps, Drizzle ORM, PostgreSQL).

### 5.1 `landing_pages`

```typescript
export const landingPages = pgTable(
  "landing_pages",
  {
    id: uuid("id").primaryKey().defaultRandom(),
    clientId: uuid("client_id")
      .notNull()
      .references(() => clients.id, { onDelete: "cascade" }),

    // Identity
    title: text("title").notNull(),                             // internal name, shown in back-office list
    slug: varchar("slug", { length: 100 }).notNull().unique(),  // URL: /lp/[slug]
    status: varchar("status", { length: 20 }).notNull().default("draft"),
    // draft | generating | ready | published | archived

    // Brief & generation inputs
    brief: text("brief").notNull(),                             // raw brief text from the form
    language: varchar("language", { length: 5 }).notNull().default("EN"), // from client.primaryLanguage

    // Generated content (structured JSON — mirrors LLM output schema)
    sections: jsonb("sections").$type<LandingPageSections>(),

    // Manual overrides (JSON map: sectionKey → overridden text)
    manualOverrides: jsonb("manual_overrides").$type<Record<string, string>>(),

    // Visual assets
    logoUrl: text("logo_url"),                                  // SharePoint URL or null (uses client logo)
    visualAssets: jsonb("visual_assets").$type<string[]>(),     // array of SharePoint URLs

    // Palette overrides (if different from client defaults)
    paletteOverride: jsonb("palette_override").$type<{
      primaryColor?: string;
      secondaryColor?: string;
      backgroundColor?: string;
    }>(),

    // Layout
    sectionsEnabled: jsonb("sections_enabled").$type<{
      features: boolean;
      socialProof: boolean;
    }>().default({ features: true, socialProof: false }),

    // SEO options
    noIndex: boolean("no_index").notNull().default(false),

    // Cost tracking
    totalTokenCost: integer("total_token_cost").default(0),     // cumulative tokens across all generations
    rawLlmOutput: text("raw_llm_output"),                       // last raw LLM response (debug)

    // ClickUp integration
    clickupTaskId: text("clickup_task_id"),

    // Timestamps
    publishedAt: timestamp("published_at"),
    createdBy: text("created_by").notNull(),
    createdAt: timestamp("created_at").notNull().defaultNow(),
    updatedAt: timestamp("updated_at").notNull().defaultNow(),
  },
  (table) => [
    index("idx_landing_pages_client").on(table.clientId),
    index("idx_landing_pages_status").on(table.status),
    index("idx_landing_pages_slug").on(table.slug),
  ]
);
```
